# 恢复、隔离与失败处置参考

本文件是 `coding-review-pipeline` 的恢复与失败速查，不重复计划确认、编码、逐任务审查和集成审查的核心流程。任何恢复动作都以工作区事实、线程状态和可复验输出为准。

## 基线改动文件台账

首次派发前由主会话记录以下字段；不得只采用 worker 自报。

| 字段 | 必填内容 |
|---|---|
| 起始状态 | `git status --short` 的原始输出与执行时刻；失败也原样记录错误 |
| 允许写集 | 每个 coding 子任务可新建或修改的绝对路径集合 |
| 只读依赖 | 可读取但不可修改的文件、接口或前驱产物 |
| 已有脏文件 | 起始状态中的已跟踪改动、未跟踪文件及其原有归属；空集合也明确记录 |
| 实际变化 | worker 自报、状态新增和内容变化三者的并集 |
| 责任归属 | 子任务、轮次、派发时刻、结束时刻及对应 review 结论 |

指纹不是默认全量步骤。仅当目标文件起始已脏、含未跟踪文件、存在并发写入风险，或 Git 状态不足以区分前后变化时，才记录相关文件的内容哈希、大小和修改时间。干净且单写者的已跟踪文件以 Git diff 为主，避免制造无效台账。

若目录不是 Git 仓库，台账标记 `NON_GIT`，保存目录清单和必要的条件指纹；不得把 `git status` 失败解释为工作区干净。非 Git 文件没有可靠恢复基线时，停止覆盖、删除或重建，并请求用户决定。

每轮结束后重新核对状态。已有脏文件若本轮未变，不计入本次产出；若在原有改动上继续修改，必须显式标注。发现允许写集之外的新变化时，冻结后续写入并进入失败表。

## 并行文件隔离与依赖拓扑

- 每个 coding 子任务只有一个明确的允许写集；并行任务的允许写集必须两两不相交。
- review 线程只读，不进入写冲突集合，也不得自行修复。
- 后继任务可把前驱产物列为只读依赖，但不得修改前驱的文件范围。
- 存在同文件写入、生成物覆盖、共享配置更新或先后语义依赖时，合并任务或建立有向依赖边，按拓扑顺序串行。
- 只有入度为零、文件范围不重叠且资源可用的任务可进入同一并行批次。
- 一个独立分支失败不阻塞其他无依赖分支；依赖它的后继保持等待，不得绕过前驱结论。

派发前保存“任务 → 允许写集 → 只读依赖 → 前驱 → 当前轮次”的快照。派发后范围不可静默扩大；需要扩展时先停止该任务，由主会话重画边界和依赖图。

## 线程生命周期与及时回收

线程状态统一为：`未派发`、`运行中`、`等待补充`、`已完成待收集`、`需修正`、`已批准`、`已回收`、`不可恢复`。

- 派发后立即登记线程标识、角色、子任务、允许写集和轮次。
- 结果到达后先收集完整输出与工作区事实，再改变状态；不要因一句“完成”直接批准。
- `fix-first` 对应的 coder 线程若仍可用则保留用于定向修正；不可用时才创建同职责后续线程。
- 已批准且不再需要追问、修正或恢复的线程立即回收，释放并发名额。
- 仍在运行、等待必要证据或承担后续修正的线程不得提前关闭。
- 进入集成审查前，计划要求的 boundary review 必须获得 `ship`，其余子任务必须完成主会话独立复验，且已完成线程均已回收。
- 中断恢复时先查询已有线程并收集完成结果，不得先重复派发。

## 中断恢复决策表

| 已核实状态 | 恢复动作 | 禁止动作 |
|---|---|---|
| coder 仍在运行 | 结果是下一步依赖时等待，否则继续无依赖工作 | 重复派发同一写集 |
| coder 已结束且有明确落盘变化 | 先做主会话独立复验；计划要求 boundary review 时再用实际清单发起审查 | 仅凭 coder 摘要判定完成 |
| coder 已结束但产出缺失或模糊 | 核对状态、diff 和条件指纹；只重派缺失范围 | 覆盖已有变化或重做完整任务 |
| review 返回 `fix-first` | 将结构化发现路由给原 coder；不可恢复时创建后续 coder | 让 reviewer 修改文件 |
| boundary review 返回 `ship` | 回收对应线程；继续其后继或其他未完成任务 | 把审查结论当作主会话复验 |
| 所有任务已实施并完成必要复验 | 确认线程回收和台账一致后进入 fresh integration review | 遗漏未跟踪文件或范围外变化 |
| integration review 返回 `fix-first` | 按文件归属拆回对应子任务，修正后重做主会话复验与 fresh review | 把跨文件发现交给无归属 worker |
| integration review 返回 `ship` 但验证未完成 | 从最新必要验证继续并记录完整证据 | 把审查结论当作验证通过 |
| 工作区出现未知变化 | 冻结写入，保存证据并请求用户判定归属 | 猜测归属、静默吸收或破坏性回滚 |
| 非 Git 且缺可靠基线 | 只做可证明安全的只读核对并上报 | 删除、覆盖或猜测重建 |

恢复后复用模型或推理强度前，必须确认当前运行时仍支持既有选择；上下文缺失或能力失效时暂停派发并请用户重新选择，禁止静默替换。

## 最多三轮修正

逐任务 review 和集成 review 分别独立计轮。一次“发现 → coder 修正 → 重新 review”计一轮，轮次与发现、实际文件、验证证据绑定。第 1 至 3 轮允许继续；第 3 轮仍未批准即停止该闭环，汇总每轮未收敛点、重复失败证据和当前工作区状态，上报主会话或用户。不得以换线程、改写措辞或拆分同一问题清零计数。

`fix-first` 适用于规格正确、根因充分且发现可在原边界内机械修复；`rethink` 适用于接口或算法判断错误、根因不足、发现跨越原任务边界，或同类缺陷重复出现。进入 `rethink` 后先由主会话修正规格与依赖图，再决定是否开启下一轮。

## If-Then 失败表

| If（触发） | Then（立即处理） | 证据与升级条件 |
|---|---|---|
| 工具不可用，或运行时不支持所选模型能力/推理选项 | 编码前停止，读取当前能力并请用户重选 | 记录缺失能力与原始错误；禁止静默降级或主会话代写 |
| coder 因规格矛盾、文件不可写或缺必要输入而阻塞 | 收集具体阻塞证据，由主会话补齐规格后再派发 | 只重派已补足的范围；同因未消除不得重试 |
| coder 中断、超时或返回模糊 | 先查线程、台账、状态、diff 与条件指纹 | 已落盘部分进入 review；仅缺失部分可重派 |
| 发现允许写集之外的变化 | 立即冻结后续写入并向用户报告 | 给出路径、前后状态、发现时刻；未定归属前不得吸收或回滚 |
| review 发现明确、局部且规格仍成立 | `fix-first`：路由给原归属 coder 定向修正 | 修正后重新 review，并递增该闭环轮次 |
| review 暴露根因不足、设计错误、跨范围影响或重复缺陷 | `rethink`：停止修正，由主会话补根因、重定规格和拓扑 | 新规格明确前不得沿原方向继续试错 |
| 编译、测试或检查失败 | 将失败按文件和责任范围路由给对应 coder，修正后重跑同命令 | 记录命令、完整关键输出、退出码、失败数；仍失败则上报未完成项 |
| 达到线程上限 | 回收已完成且无后续用途的线程，再按拓扑分批或串行 | 不关闭运行中或待修正线程；不得用重叠写集强行合并并行 |
| 逐任务或集成修正已满 3 轮 | 停止该闭环并汇总累计发现 | 上报未收敛原因、各轮证据和安全停点，不得改名重开规避上限 |
| 当前目录不是 Git 仓库 | 标记 `NON_GIT`，采用目录清单与条件指纹，只做可审计动作 | 无可靠基线时停止写入性恢复，交由用户决定 |
| `scripts/review_preflight.py` 未运行或无法启动 | review 子代理在 GAPS 中报告并停止：确定性前置（detect/normalize/negative coverage/P0-P3）不可跳过 | 记录原始错误与退出码；不得跳过 preflight 直接给 verdict |
| `ocr` 命令缺失或 `ocr delegate rule` 失败（optional enrichment） | review 继续：preflight 输出 `ocr.state=skipped` 并附 reason，审查照常按 machine findings/coverage/context 完成，绝不 STOP | 记录 SKIPPED 与 reason；可选给出 `npm install -g @alibaba-group/open-code-review` 及 Node ≥14、Git ≥2.41 提示，不因 ocr 不可用重新派发 reviewer |
| preflight 的 findings / coverage 与 change facts 明显不符（如 `--facts` 文件缺失或内容过旧） | 核对 `--facts` 路径与 change_facts.py 最新输出，修正后重跑 preflight | 疑似漏审时上报主会话核对，不得静默接受异常覆盖 |

## 完整反模式清单

以下任一项出现即视为恢复或失败处理不可信，必须停止并纠正：

- 主会话代写项目源码，绕过 coder 与 review 审计链。
- 工具、模型能力、验证或审查失败后静默降级。
- 信任 worker 的完成、文件或测试声明，不核对工作区与命令证据。
- 向其他 worker 转发主会话或 worker 的 raw 对话、提示词、内部推理或未经整理的中间状态；只传任务契约和结构化必要证据。
- 对允许写集重叠的 coding 子任务并行派发。
- 未检查线程与工作区就重复派发可能已经落盘的任务。
- 使用破坏性回滚覆盖用户改动、worker 改动或未知并发变化。
- 没有最新命令、退出码、失败数和实际文件清单就声称完成或通过。
- reviewer 自行修改或修复文件；reviewer 只能提出带位置与证据的结论。
- 把仓库原有测试、用户要求保留的测试或无法确认归属的测试误当临时测试删除。

临时测试只在确认“本次新建、仅用于临时验证、用户未要求保留”三项同时成立时清理；其余测试一律保留并上报归属疑问。
