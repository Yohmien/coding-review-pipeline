# 验证路由

## 父会话独立复验

交付前由父会话独立完成以下检查，不以 coder 或 reviewer 的结论代替：

- 检查 `git status`、完整 diff 与允许修改范围，确认保留既有改动且没有越界文件。
- 按仓库已有构建系统、脚本和规约选择验证命令，并亲自重跑所有用于结论的命令。
- 核对命令输出、退出码、测试失败数和未执行项；部分验证不得表述为全部通过。

## 工具与命令路由

- 遇到缺陷或异常行为，先使用 `systematic-debugging` 定位根因。
- 实现可测试功能或修复缺陷时，使用 `test-driven-development` 建立失败到通过的证据。
- 宣称完成、修复或测试通过前，使用 `verification-before-completion` 复核最新证据。
- 验证命令以仓库实际存在的构建文件、wrapper、脚本和测试设施为准，不跨生态硬编码命令。
- 仅当项目确为 Java/Maven 且相应设施存在时，才条件使用 `mvnd`、ArchUnit、Maven Enforcer 或 L2 启动测试；先确认项目提供对应命令、规则、profile 或测试类，再执行。

## 测试三档

对每项改动明确归入一档，并记录依据：

1. **可测**：存在可重复、可自动判定的行为；必须新增或更新测试并提供红绿证据。
2. **客观不可测**：受缺失环境、外部系统、硬件或不可获得数据阻断；说明阻断事实、已做替代检查及残余风险。
3. **用户批准豁免**：本可测试但用户明确同意不补或不跑；记录批准范围，不把豁免写成验证通过。

## 红绿证据

缺陷修复优先保留自然红绿证据：修复前用稳定复现命令得到预期失败，修复后用同一命令得到通过。可测功能优先先写测试并确认实现前失败，再实现至通过；失败必须由目标行为缺失导致，而不是语法、依赖或环境错误。

若实现前无法保留自然红态，但需要证明测试确实能捕获回归，使用五步红变体：

1. 运行新增或修改的测试，确认当前为绿。
2. 对目标行为施加一个最小、可逆且明确标注的临时变体。
3. 用同一命令确认测试按预期变红，并记录失败原因。
4. 精确恢复临时变体。
5. 再次用同一命令确认恢复为绿，并核对 diff 不含临时变体。

不得用无关失败充当红态，也不得只报告“已运行”。

## 临时验证清理

只清理明确标注为 ephemeral 的临时 harness，并在清理前确认它不是交付物。禁止删除用户要求的测试、回归测试或任何正式测试。清理后重新检查工作区与完整 diff，确保没有误删或遗留临时变体。

## 最终证据

最终报告逐项列出：验证目的、实际命令、退出码、通过/失败数及关键结果。未执行的命令或测试必须明确列出原因、影响与残余风险；不能获得可靠失败数时也要如实说明。
